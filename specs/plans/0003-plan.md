## Ordered steps

1. **`Room.BusinessWindowOn` plus grid alignment**, with their tests including a daylight-saving day.
   These are the two pieces of time arithmetic everything else rests on, and the two most likely to be
   wrong.
2. **The search algorithm for one room**: subtract overlapping bookings from the day's window, walk the
   free stretches, align each one's start up to the next local quarter hour, and emit a candidate when
   the length fits. Tests for every case in the spec.
3. **Validating candidates through the same rules.** Each candidate is passed through `Booking.Create`
   before being returned (see the risk below) so the search cannot propose something the booking path
   would refuse.
4. **The port method** and its in-memory implementation.
5. **The use case**: room selection, window clamping, merge, order, truncate.
6. **The endpoint**, query validation and the response DTO.
7. **HTTP tests and the round-trip property test**, then the documentation clauses.

## Risks & open questions

- **The strongest promise in the spec is also the easiest to break.** AC-5 says a returned candidate is
  never refused by a booking request, and the obvious way to break it is to reimplement the rules
  inside the search. *Recommendation:* the search builds each candidate and runs it through
  `Booking.Create` — the same function the booking path uses — discarding any that are refused. The
  rules then cannot drift apart, and the round-trip test becomes a check on that wiring rather than a
  coincidence. It costs a throwaway `Guid` per candidate, which is nothing at this scale.
- **Daylight-saving days have 23 or 25 hours.** Iterating "every quarter hour from the local open time"
  can silently skip or double an hour. *Recommendation:* derive candidate starts from the UTC window
  and align them by converting to local time, rather than generating local times and converting
  forward. The DST test in step 1 is what proves it.
- **"Contiguous free stretch" needs a precise definition** or the tests become arguments.
  *Recommendation:* a stretch is a maximal interval inside one local day's opening hours that overlaps
  no booking; back-to-back bookings therefore split a day into stretches, and a booking that ends
  exactly when opening hours begin does not create an empty one.
- **The 31-day window and the 90-day horizon interact.** A window of 31 days starting on day 80 reaches
  past the horizon. *Recommendation:* clamp to the horizon and return what fits, rather than refusing
  the query — the caller asked a reasonable question and deserves the answer that exists.
- **Ordering ties are not hypothetical:** three rooms with identical hours produce identical candidate
  starts. *Recommendation:* order by start, then room name ordinally — the same comparison S-001 uses
  for listing rooms, so the two endpoints agree.
- **The cap can hide the answer the caller wanted.** *Recommendation:* apply it after ordering so the
  earliest candidates survive, and leave paging out of this slice; if truncation turns out to matter in
  practice, that is a spec of its own rather than a flag.

## Deviations recorded at build time

- **"The earliest candidate in a stretch" became "the earliest *acceptable* candidate".** Writing the
  tests exposed a hole in the plan: validating candidates through `Booking.Create` means the earliest
  one can be refused — a stretch beginning exactly at the current instant fails BR-8, which is strict
  — and the stretch would then have been discarded whole. The search now walks the grid forward until
  a candidate passes or the stretch runs out. Same design, one word different, and the word mattered.
- **`Room.BusinessWindowOn` handles an invalid local time.** If a zone ever shifted during business
  hours, the opening time might not exist on the clock that day. It advances to the first moment that
  does. Not reachable with a 09:00 opening, but the alternative was silent nonsense.
- **The domain search takes an `attendeeCount`** so BR-6 is judged by the same probe as every other
  rule, rather than only by the room filter in the use case.
- **After review: each grid step is re-aligned to the room's local quarter hour** instead of advancing
  by a flat fifteen minutes. No test can distinguish the two — every real zone's offsets and
  daylight-saving deltas are multiples of fifteen minutes, so the flat step happens to stay aligned —
  but depending on that coincidence is not the same as being correct, so the code no longer does.
- **After review: the criterion map above was corrected** to the names the tests carry. It was written
  before the tests existed and had drifted.
