5. **The cross-slice tests**: a cancelled window is bookable again and is proposed again.

## Risks & open questions

- **Cancelling is two steps — find, then remove — and that is a race.** Two callers can both pass the
  BR-9 check and both try to remove. *Recommendation:* let `RemoveAsync` be the single arbiter: it
  removes under the lock and reports `booking.not_found` if the booking has already gone, and the use
  case returns whatever it says. The loser gets a `404`, which is the truthful answer. Proven by a
  parallel test at the adapter, the same way BR-2 is.
- **Generalising the port touches shipped code (S-003).** *Recommendation:* do it now, while there are
  exactly two callers and the tests for the first one are green. The alternative is two overlapping
  listing methods forever, and the second caller would copy the wrong one eventually.
- **Extracting the query parsing also touches S-003's endpoint.** *Recommendation:* extract it. Two
  endpoints that both take a UTC window must refuse a malformed one identically, and the cheapest way
  to guarantee that is one function rather than a convention.
- **The two caps differ (50 suggestions, 200 bookings) and will look arbitrary.** *Recommendation:*
  state the reason where the numbers live — suggestions are more useful when there are few, whereas a
  truncated list of facts hides reality. If it still reads as arbitrary in review, the fix is paging,
  which is its own spec.
- **AC-7 is the first behaviour that spans two slices.** Nothing in S-003 knows about cancellation, and
  nothing in this slice knows about the search. *Recommendation:* an HTTP test that books, cancels and
  re-searches — the only way this stays true as either side changes.
- **`EnsureCancellableAt` returns `Result<Booking>`** rather than a non-generic result, which is the
  third time that type has not been needed. If a fourth use case wants a value-less outcome, that is
  the moment to add it, not now.

## Deviations recorded at build time

- **`QueryWindow` was extracted into the application layer as well**, not just the query parsing in
  the API. The 31-day rule and the "must move forwards" check existed in the availability use case and
  the listing needed both; one function now owns the rule instead of two copies agreeing by habit.
- **The test stubs moved to `tests/RoomBook.Api.Tests/Stubs/`.** The availability cap test had them as
  nested classes and the listing cap test needed the same two; a third copy would have been the moment
  they started drifting.
- **`ListBookingsUseCase` loads the rooms** to order by room name, because a booking carries a room
  identifier and not a name. The alternative was ordering by identifier, which would have made this
  endpoint disagree with the other two about what "in order" means.
- **Three listing tests were passing for the wrong reason** before the assertions caught it: the shared
  request helper defaults to Monday and the tests query Tuesday, so the bookings they created sat
  outside the window. One of them — "a cancelled booking is not listed" — would have passed forever
  without ever cancelling anything. The tests now build their own Tuesday bookings and the
  cancellation case asserts the booking is present *before* it is cancelled.

### After review

- **Two listing tests added**: a booking straddling the window edge is included (AC-8 says "touches",
  not "sits inside"), and a window of exactly 31 days is accepted — the availability endpoint already
  had that pin and this route did not.
- **The `404` from cancelling twice now asserts the whole problem document**, not only its code. A 404
  is as much part of the error contract as a 409, and the envelope is what a client parses.
- **`ListBookingsUseCase` no longer loads every room when one was named.** The room found while
  validating the filter is the only name the ordering can need.
