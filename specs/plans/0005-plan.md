## Ordered steps

1. **Extract `RoomBook.Infrastructure`** with the store, the schema and idempotent seeding, and teach
   the architecture rules about it. Those rules will fail until told — by design, and a good first
   signal that the guards work.
2. **The read paths**: `SqliteRoomRepository` and the booking queries. `/rooms`, `/availability` and
   the listing go green against real SQL before anything writes.
3. **The conditional insert** (BR-2 atomic, no port change), with the 64-thread test retargeted.
4. **The port change and the conditional delete** for BR-9, reporting the truthful code: deleted,
   already started, or gone.
5. **Delete the in-memory adapters** and point the test host at SQLite.
6. **The restart test** on a temp file — the only proof of persistence that actually restarts anything.
7. **ADR-0005 and the documentation**, then the spec checklist.

## Risks & open questions

- **Storing instants as text invites format bugs.** Overlap and horizon comparisons are inequalities,
  and lexicographic comparison of ISO-8601 only works if every value is fixed-width UTC.
  *Recommendation:* store `start` and `end` as **integer UTC ticks**. The API never sees them, the
  comparisons are exact, and no format can drift. Business hours become minutes from midnight.
- **SQLite serialises writers.** The 64-thread concurrency test will meet `SQLITE_BUSY`.
  *Recommendation:* one writer connection owned by the store, `busy_timeout` set, WAL for file mode.
  If that turns the concurrency test flaky rather than slow, stop and report (R-03) — a flaky test
  here would be hiding exactly the guarantee the slice is about.
- **An in-memory SQLite database lives only while a connection is open.** *Recommendation:* the store
  holds one keep-alive connection for the host's lifetime, and each test host gets a uniquely named
  database so two hosts never share one.
- **The conditional delete can refuse for two different reasons** — the booking has started, or it was
  never there. *Recommendation:* after a delete that changed nothing, ask whether the row exists, in
  the same transaction, and report `booking.cancel_after_start` or `booking.not_found` accordingly. The
  caller gets the truth rather than whichever answer is cheaper.
- **The domain's BR-9 check now sits alongside the SQL condition**, which looks like the same rule in
  two places. *Recommendation:* keep both and say why — the domain owns the rule and answers without a
  round trip; the SQL condition exists so the answer cannot be overtaken by the clock. The same shape
  as the attendee-count guard in S-002.
- **Seeding runs on every start.** *Recommendation:* `INSERT OR IGNORE` keyed by the published
  identifiers, so a second start changes nothing (AC-11) and a client's stored identifier stays valid.
- **`scripts/check` must need no service** (AC-8). *Recommendation:* SQLite satisfies this by
  construction; the check step stays exactly as it is, which is itself part of the evidence.
